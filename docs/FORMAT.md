# Формат образа NMGLFDFS, версия 1

Образ — обычный файл. Размер блока везде **4096** байт. Числа — little-endian. Файловая система одноуровневая: одно B-дерево и на индекс, и на каталоги, и на экстенты, по тому же принципу, что FS-дерево Btrfs, но без подтомов, без дерева свободных экстентов и без дерева контрольных сумм отдельно от элементов.

## Карта тома

| Блок | Содержимое |
| --- | --- |
| 0 | суперблок |
| 1 | резервная копия суперблока (та же самая запись) |
| 2 … 2+N−1 | битовая карта занятости, N блоков |
| далее | корень B-дерева, затем данные и новые версии узлов |

Бит `b` в карте: байт `b/8`, бит `b mod 8` (младший бит — меньший номер). 1 — занят. Блоки 0…корень включительно помечаются занятыми при `mkfs`. Карта обновляется на месте. Это сознательное упрощение относительно дерева свободного места Btrfs.

## Суперблок

Контрольная сумма CRC32C (Кастаньоли) покрывает байты `[0, 248)` и лежит в поле по смещению 248. При проверке это поле обнуляется.

| Смещение | Размер | Поле |
| --- | --- | --- |
| 0 | 8 | сигнатура `NMGLFDFS` |
| 8 | 4 | версия, сейчас 1 |
| 12 | 4 | флаги: бит 0 = SLEEP, бит 1 = WIPED |
| 16 | 4 | размер блока, 4096 |
| 20 | 4 | число блоков битовой карты |
| 24 | 8 | всего блоков в образе |
| 32 | 8 | номер первого блока карты (2) |
| 40 | 8 | номер блока корня B-дерева; 0, если SLEEP или WIPE |
| 48 | 8 | поколение (растёт на каждую запись метаданных) |
| 56 | 8 | следующий свободный номер inode |
| 64 | 8 | число свободных блоков |
| 72 | 4 | число итераций PBKDF2-HMAC-SHA256 |
| 76 | 4 | резерв |
| 80 | 16 | соль KDF |
| 96 | 16 | UUID образа |
| 112 | 32 | ключ ФС, зашифрованный ChaCha20 под ключом из пароля; нули при SLEEP/WIPE |
| 144 | 64 | блоб SLEEP (используются первые 48 байт) |
| 208 | 32 | проверка пароля: `SHA-256(KEK \|\| соль \|\| "NMGLFDFS-VERIFIER")` |
| 240 | 8 | счётчик записей блоков данных (`write_seq`) |
| 248 | 4 | CRC32C |

`KEK = PBKDF2-HMAC-SHA256(пароль, соль, итерации, 32)`. Новый том получает 200000 итераций. Число лежит в суперблоке и при открытии берётся оттуда.

Обёртка ключа: `wrap = SHA-256(KEK \|\| "WRAP-NMGLFDFS")`, nonce — первые 12 байт соли, ChaCha20 с счётчиком 0 поверх 32 байт случайного ключа ФС.

Из ключа ФС:

- ключ данных `SHA-256(ключ ФС \|\| "DATA-KEY")` — конвейер блоков файла;
- ключ метаданных `SHA-256(ключ ФС \|\| "META-KEY")` — тела узлов дерева.

Проверка пароля не зависит от ключа ФС, поэтому неверный пароль отличается от спящего тома, а `wipe` можно обнаружить и без ключа: поле проверки затирается.

### SLEEP

В блоб кладётся открытый текст из 48 байт: номер корня (`u64`), обёрнутый ключ (32 байта), сигнатура `SLEEPv1!` (8 байт). Он шифруется ChaCha20. Ключ: `SHA-256(KEK \|\| "SLEEP-SEAL-NMGL")`, nonce — 12 байт соли. После этого в суперблоке корень и обёрнутый ключ обнуляются и ставится флаг SLEEP. `wake` расшифровывает блоб, сверяет сигнатуру и возвращает поля на место.

### WIPE

После проверки пароля (если том спал — блоб вскрывается только в памяти) обходятся узлы дерева и перезаписываются случайными данными. Затем затираются соль, обёрнутый ключ, проверка пароля, блоб SLEEP и ключи в памяти. Флаг WIPED остаётся в ясном виде. Обратной операции нет.

## Узел B-дерева

| Смещение | Размер | Поле |
| --- | --- | --- |
| 0 | 4 | сигнатура `NMTN` |
| 4 | 4 | CRC32C байтов `[8, 4096)` |
| 8 | 8 | свой номер блока |
| 16 | 8 | поколение |
| 24 | 1 | уровень (0 — лист) |
| 25 | 1 | флаги, бит 0 = тело зашифровано |
| 26 | 2 | число элементов |
| 28 | 4 | резерв |
| 32 | 4048 | тело |
| 4080 | 16 | HMAC-SHA256 (первые 16 байт из 32) |

Тело шифруется ChaCha20 ключом метаданных. Nonce — номер блока (`u64`) и младшие 4 байта поколения. Заголовок остаётся открытым, чтобы можно было проверить номер блока и CRC до расшифрования. Поверх шифртекста считается `HMAC-SHA256(ключ метаданных, байты [8, 4080))`, в блок пишутся первые 16 байт. Проверка тега идёт после CRC и до расшифрования: злоумышленник, который поправил CRC, тег без ключа не подделает. Имена, ключи индекса и параметры шифрования лежат в теле, то есть без ключа метаданных не видны.

Ключ элемента, как в Btrfs: `(objectid u64, type u8, offset u64)`. Сравнение лексикографическое.

### Лист (уровень 0)

Заголовки элементов пакуются с начала тела, данные — с конца.

Заголовок, 32 байта:

| Смещение | Размер | Поле |
| --- | --- | --- |
| 0 | 8 | objectid |
| 8 | 1 | тип |
| 9 | 3 | нули |
| 12 | 8 | offset |
| 20 | 4 | смещение данных внутри тела |
| 24 | 4 | длина данных |
| 28 | 4 | резерв |

Типы: `1` inode, `2` элемент каталога, `3` данные файла (extent).

**Inode**, 64 байта. Корень — objectid 256, дальше номера выдаются с 257.

| Смещение | Размер | Поле |
| --- | --- | --- |
| 0 | 4 | mode |
| 4 | 4 | nlink |
| 8 | 4 | uid |
| 12 | 4 | gid |
| 16 | 8 | size |
| 24 | 8 | atime, секунды |
| 32 | 8 | mtime |
| 40 | 8 | ctime |
| 48 | 8 | число блоков данных |
| 56 | 8 | inode родителя (у корня — он сам) |

**Каталог.** Ключ: objectid каталога, тип 2, offset = FNV-1a 64 от имени (при коллизии offset увеличивается, пока ключ свободен). Данные: inode ребёнка (`u64`), тип dentry (`u8`, `DT_DIR=4`, `DT_REG=8`), длина имени (`u8`), 2 байта нулей, имя без завершающего нуля. `.` и `..` в дереве не хранятся: `..` берётся из поля родителя.

**Extent.** Один элемент на логический блок файла 4096 байт. Offset ключа — смещение в файле. Данные, 48 байт:

| Смещение | Размер | Поле |
| --- | --- | --- |
| 0 | 8 | номер блока шифртекста на диске |
| 8 | 8 | метка времени, миллисекунды |
| 16 | 8 | `write_seq` на момент записи |
| 24 | 1 | метод, обязан быть равен `метка % 10` |
| 25 | 1 | резерв |
| 26 | 2 | длина осмысленного хвоста (сейчас всегда 4096, хвост за EOF — нули) |
| 28 | 4 | CRC32C всех 4096 байт открытого текста |
| 32 | 16 | HMAC-SHA256 шифртекста, усечённый до 16 байт |

Это и есть «метаданные блока»: они лежат не в самом блоке данных (блок целиком — шифртекст, чтобы смещения файла оставались кратны 4096), а в элементе дерева, и дерево зашифровано ключом, выведенным из пароля.

Тег блока: `HMAC-SHA256(ключ данных, "NMGLMAC1" ‖ номер блока ‖ метка ‖ write_seq ‖ inode ‖ смещение ‖ метод ‖ длина ‖ CRC32C ‖ 4096 байт шифртекста)`, берутся первые 16 байт. Проверка до расшифрования. Совпадение CRC открытого текста после этого остаётся второй проверкой.

### Внутренний узел

Элементы по 40 байт подряд с начала тела, не больше 101 штуки:

| Смещение | Размер | Поле |
| --- | --- | --- |
| 0 | 8 | objectid |
| 8 | 1 | тип |
| 9 | 7 | нули |
| 16 | 8 | offset |
| 24 | 8 | номер блока потомка |
| 32 | 8 | поколение потомка |

Поиск идёт в потомка с наибольшим ключом, который не больше искомого. Если искомый ключ меньше всех, берётся самый левый потомок.

При нехватке места в листе элементы делятся пополам, правая половина пишется в новый блок, а в родителя вставляется разделитель. Если листа-корня больше нет места, создаётся новый внутренний корень. Точно так же делится полный внутренний узел (101 потомок): левая половина остаётся на месте, правая пишется в новый блок, разделитель — ключ первого элемента правой половины — уходит в родителя. Если полон сам корень, над ним появляется новый корень на уровень выше. Запись узла никогда не перезаписывает живой блок: выделяется новый, родитель переводится на него, старый освобождается только после записи суперблока. Если выделить блок не удалось или глубина достигла 8, операция отменяется и возвращается ENOSPC или EIO; биты только что выделенных блоков снимаются, суперблок не меняется.

## Конвейер блока данных

Открытый текст — 4096 байт. Входы, все участвуют в выводе подключей: ключ данных, метка времени, `write_seq`, смещение в файле, номер inode.

**Переворот битов.** `SHA-256(ключ данных \|\| timestamp u64 \|\| write_seq u64 \|\| смещение u64 \|\| inode u64 \|\| "NMGL-BITFLIP")` даёт ключ ChaCha20. Nonce — `timestamp` (8 байт) и младшие 4 байта `смещение XOR inode XOR write_seq`. Счётчик 0. Гамма накладывается XOR. Дополнительно для байта `i`: если `(бит timestamp номер i mod 64) XOR (popcount(timestamp) mod 2) = 1`, байт инвертируется. Повтор того же шага возвращает исходные данные.

**Метод `timestamp % 10`.** Подключ: `SHA-256(ключ данных \|\| байт метода \|\| timestamp \|\| write_seq \|\| смещение \|\| inode \|\| "NMGL-METHOD")`. Nonce ChaCha20: `timestamp XOR write_seq` (8 байт) и младшие 4 байта `смещение XOR inode XOR (метод * 0x10001)`. Счётчик 1.

Шифрование: переворот битов, затем математический слой, затем XOR гаммы ChaCha20. Расшифрование: XOR той же гаммы, обратный слой, переворот битов.

Слои 0…9 перечислены в README. Константа умножения по модулю 2^64 — `0x9E3779B97F4A7C15` (обратная `0xF1DE83E19937733D`). Поле GF(2^8) — многочлен AES `0x11B`, множитель `0x53` (обратный `0xCA`).

## Чего в формате нет

Отдельного дерева контрольных сумм, журнала, подтомов, квот, сжатия и снимков. CRC32C проверяет, что расшифрование дало тот же текст, что записывали, и что узел не разрушен случайно. Подмену ловит HMAC-SHA256 (16 байт из 32) на каждом узле и на каждом блоке данных. Это не защита от подмены образа целиком на более старую копию.
